Click-to-play on registry sources — diagnosis, fixes, and an honest account of what is verified and what is not.

lane hp-player date 2026-08-21 owned path js/app.js branch worktree-agent-aa7ac5e16e1a592a6 commit 5d2fcf4 server localhost:8061

The headline

Click-to-play works, and it was never broken. The defect handed to this lane — "canvas click on a flown-to registry tile did NOT open the player overlay" — is a verification-harness artifact, not an application bug. A real mouse click on a registry tile opens the player and starts playback. Two genuine defects surfaced during the investigation, and both live outside this lane's owned file; both were escalated rather than patched.

Why the original verification failed

The suggested drive sequence was App.state().wall.focusIndex(0) to fly to a tile, then click it. But focusIndex(n) selects the tile as part of flying to it, and the wall treats a click on an already-selected tile as a deselect, not a select. So the click toggled the selection off and flew the camera home instead of firing onSelect. Measured directly:

focusIndex(4)  -> selected: 4,    cam {x:200, y:-660, zoom:1.346}
real click     -> selected: null, cam {x:0, y:0, zoom:1}
                  onSelect fired: 0    player opened: false

A second, compounding artifact wasted time early on and is worth recording: reading the DOM in the same synchronous tick as the click reports a false negative. The player overlay mounts asynchronously, so document.querySelector('.plr-root') immediately after a select returns null even when the player opens correctly milliseconds later. Any future verification of this app must poll or use a MutationObserver, never a same-tick check.

Proof that the path is sound

With nothing pre-selected and a real synthetic mouse click on a visible registry tile, the full chain fires end to end: wall click → onSelect → onWallSelect → it.meta.hpUrl detected → playRegistry → window.Player.play → overlay open with the right title and a live video element.

  -> onSelect fired: 1
  -> Player.isOpen(): true      .plr-root.plr-in present: true
  -> title: "Mux HLS test stream"
  -> currentTime 6.29s, readyState 4, duration 634.6s, 90s buffered

Defect 1 — crossorigin blocks every non-CORS source

Not my file. Escalated and routed to lane hp-motion (owner of js/player.js). Deliberately NOT shimmed here — the orchestrator and I agreed that two lanes patching one symptom in two files is how a wrong guess becomes load-bearing.

js/player.js hard-sets crossorigin="anonymous" on the <video> element it creates. That forces a CORS-mode media fetch. Any source whose host omits Access-Control-Allow-Origin is then refused by the browser and never plays.

<video playsinline webkit-playsinline preload="metadata"
       crossorigin="anonymous"
       src="https://test-videos.co.uk/.../Sintel_720_10s_5MB.mp4">

networkState 3 (NETWORK_NO_SOURCE) · error.code 4 (MEDIA_ERR_SRC_NOT_SUPPORTED)
readyState 0 · currentTime 0 · duration null

Every registry host was probed directly. All are alive — this is emphatically not ORACLE §5 stream-rot, and swapping URLs would be the wrong fix:

206 video/mp4            no-cors-header   test-videos.co.uk .../Big_Buck_Bunny_720_10s_5MB.mp4
206 video/mp4            no-cors-header   test-videos.co.uk .../Sintel_720_10s_5MB.mp4
206 video/mp4            no-cors-header   test-videos.co.uk .../Jellyfish_720_10s_5MB.mp4
206 video/mp4            no-cors-header   media.w3.org/2010/05/sintel/trailer.mp4
206 audio/mpegurl        ACAO: *          test-streams.mux.dev/x36xhzz/x36xhzz.m3u8
206 application/x-mpegURL no-cors-header   devstreaming-cdn.apple.com/.../master.m3u8

Corroborating signal: a page-context fetch() of the same MP4 returns "Failed to fetch" while curl returns 206 — the signature of a CORS rejection, not a dead host. Codec support was ruled out separately (canPlayType for H.264 returns "probably").

Why this outlives the demo data. ORACLE §4 already states the rule correctly — "MP4 <video src> does NOT need CORS — only HLS does" — but the player currently forces CORS mode on MP4 anyway. So any real curated source the founder later adds from a host that omits ACAO will silently fail. The fix is to scope crossorigin to the hls.js path or make it opt-in through the Player.play opts, not to remove it blindly: subtitle fetching or canvas thumbnail capture may depend on it, and that audit belongs to the file's owner.

Defect 2 — registry lane rows render off-screen at the wall's home camera

Not my file (wall layout lives in js/wallview.js). Reported, not patched.

On #home with the camera at its home position {x:0, y:0, zoom:1}, the six registry tiles are laid out above the viewport and are not visible:

tiles[0] = { i:0, sx:640, sy:-241, vis:false }
first visible indices = [6, 7, 8, 9, 10, 46, ...]   // all addon items

Mouse-wheel panning did not move the camera either (panLockedX appears in wall state), so at present a user landing on home cannot reach the registry rows by scrolling. This matters more than a layout nit: buildHomeGroups() deliberately puts the registry first because, in the project's own words, "the registry IS the product" — and right now the product's headline rows are the ones you cannot see. Worth a decision from whoever owns the wall layout.

What this lane built

All changes are confined to js/app.js. Nothing else was touched.

1 · Registry sources in search (budget row 10)

Added registryMatches(q) — a plain case-insensitive substring match over each registry row's title, display name, and notes. The registry is a handful of curated rows, not a corpus, so anything cleverer would only add surprise.

The merge itself was placed in paintResults() rather than runSearch(), for two reasons worth recording: paintResults is the single choke point for all three search paths (exact cache hit, stale-prefix preview, and the network reply), so registry rows appear on every one of them; and because the merge runs at paint time it always reflects the current registry, even when the addon half of the result set came from cache. Registry hits are placed ahead of addon hits, with a defensive de-dupe by id (registry ids are hp:-prefixed and cannot collide today).

A second bug was found and fixed while verifying this. The first attempt still painted zero registry results, because the cold search path painted an empty wall and waited on the network — if no addon ever answered, paintResults was never called and registry hits never appeared at all. That path now paints the local registry matches immediately, and deliberately keeps the loading stage when nothing in the registry matches, so an empty registry never masquerades as "no results" while addons are still in flight.

2 · Registry items in continue-watching

A registry source has no addon behind it, so the #detail route dead-ends on it. The Continue Watching group now hands back the live Registry meta when a saved id resolves to a registry row, so the item carries hpUrl and onWallSelect replays it through playRegistry. Records whose source has since left the registry still render from the saved record rather than silently vanishing from the user's history.

On budget row 1 (410 ms vs a 150 ms budget). The latency is not spent in playRegistry or in the player's mount. The wall defers its onSelect callback until its fly-to animation completes, so the overlay cannot appear before the animation ends. Meeting a 150 ms budget therefore requires a change in js/wallview.js (fire select on commit rather than on animation end, or shorten the fly-to) — outside this lane's owned path. Reported, not attempted.

Lane discipline and escalations

  • Owned path respected. Only js/app.js was modified; git status shows a single modified file. Both defects found outside it were escalated, not patched.
  • Relayed the user's mid-session order. fire17 asked twice that the main agent be told about a new source in verified_sources.md; it was sent as a direct message with the exact diff. The line is stremio://chaturbate.stremio.homes/f/manifest.json — a Stremio addon manifest, not a registry table row, requiring addon-layer work. The orchestrator confirmed it was already routed to lane hp-catalog and that the manifest host sends access-control-allow-origin: *.
  • Declined to shim. Offered the orchestrator a lane-local workaround for the crossorigin bug and recommended against it; the orchestrator agreed and routed the real fix to hp-motion.
  • Scratchpad collision observed. A shared probe.sh in the session scratchpad was rewritten mid-run by another lane to target its own browser session. The other lane's file was left untouched and this lane moved to uniquely-named scripts. Worth a fleet convention: lane-prefix every shared-scratchpad filename.

Handoffs

  1. hp-motion (js/player.js) — scope crossorigin to the hls.js path or make it opt-in via Player.play opts. Audit first for subtitle/canvas dependencies before any blanket removal. This lane will re-verify budget rows 2 and 5 against the fix, including the Apple HLS row.
  2. hp-motion (js/player.js) — continue-watching resume does not restore the saved offset. Progress is written correctly (hp:6n6hxw @ 15.1 s), and the item replays, but starts at 0. Suspect the resume seek is applied on a loadedmetadata path that the hls.js blob source misses; this was not diagnosed, only observed.
  3. Wall-layout owner (js/wallview.js) — two items: registry lane rows render above the viewport at the home camera and are unreachable by wheel pan; and onSelect fires only after the fly-to animation, which is what puts budget row 1 at ~400 ms.
  4. Whoever writes ORACLE §8 — two entries earn their place: a same-tick DOM check after a click is a false negative, the overlay mounts asynchronously; and focusIndex() selects, so a following click deselects — never drive click-to-play through focusIndex. The orchestrator said it would log both.
  5. Fleet convention — lane-prefix shared-scratchpad filenames to prevent the collision described above.
