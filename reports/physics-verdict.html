The Transport-Law Verdict

A browser cannot play an arbitrary TCP-only BitTorrent magnet without someone putting a node in the byte path. This is not a difficulty rating and not a hedge — it is a proof, built from the four transports a browser can actually open, and confirmed by live measurement against a healthy 54-seeder swarm that contains exactly zero peers a browser can talk to.

the constraint everything is measured against

The law

fire17 — verbatim, non-negotiable

Any node we run may relay handshakes/signaling ONLY. It must NEVER carry file bytes. Files flow peer→browser directly, or not through us. A bridge/proxy that re-serves torrent bytes to the browser VIOLATES the law and is a FAILED result — even if it "works".

Everything below is judged by that single sentence. A path that moves the movie is not a success if our node touched the bytes; a path that fails honestly is a result worth publishing. The verdict on this page is the honest one.

VERDICT: IMPOSSIBLE — for arbitrary TCP-only content the user does not already have. A proof, not a hedge.

the mechanism

Four transports, and there is no fifth

A browser obtains bytes over exactly four transports. Every one of them requires the far side to complete a specific handshake before a single byte moves. A vanilla BitTorrent swarm peer — unmodified, the kind that actually holds this movie — performs none of them.

A raw BitTorrent peer answers a TCP connect with the 19-byte \x13BitTorrent protocol handshake, or it answers uTP — a bespoke UDP framing with LEDBAT. It speaks neither ICE nor DTLS nor HTTP nor QUIC. The mismatch is total, and it is not a configuration problem: the peer cannot be modified, and the browser cannot emit raw packets to meet the peer on the peer's own protocol.

Why the three obvious escapes are closed

  • There is no fifth transport. Direct Sockets (TCPSocket/UDPSocket) exists in Chromium, but it ships only inside Isolated Web Apps — and IWAs install only on Chrome-Enterprise-managed ChromeOS. It is never available to an ordinary https:// page, which is what this app is.
  • A signaling relay changes introductions, not protocol. The law permits us to relay SDP/ICE all day. It buys nothing here: once introduced, the browser can still only offer ICE+DTLS, and the raw peer still cannot answer it.
  • TURN is the only ICE path to a non-STUN host — and TURN relays the media. By definition a TURN server carries the bytes. That is a byte-path node, which the law forbids outright. Excluded.

The single cleanest statement of the wall: every transport a browser can dial requires a handshake that a raw TCP/uTP BitTorrent peer cannot perform, and the browser cannot drop to the peer's protocol to meet it.

The wall. Four arrows leave the browser; none of them lands. The relay above is allowed by the law and still cannot help — it moves introductions, not protocols.

the second, independent proof

The bootstrap paradox

Suppose we give up on reaching the classic swarm and imagine a pure browser-to-browser WebRTC swarm instead — browsers seeding to browsers, no node in the byte path, perfectly law-compliant. It cannot start.

To seed content over WebRTC, a browser must first possess the bytes. A browser can only get bytes over the four transports above. For content that lives only in a TCP/uTP swarm, the genesis browser could only have obtained it from a byte-path node — a hybrid seeder, a mirror, a gateway — which violates the law the moment it happens, even once.

the paradox, exactly

No byte-path node ⇒ no genesis seeder ⇒ no browser WebRTC swarm ever forms. The first WebRTC seeder cannot exist without a byte-path node, because WebRTC-seeding presupposes already holding bytes that only TCP/uTP could have delivered.

This is why the verdict is a proof and not a measurement artifact. Even if every wall on the transport side were somehow lifted tomorrow, the swarm for a given title still has to be seeded by someone, and under the law that someone cannot be us.

the sharp boundary

The one compliant browser-P2P mode

There is exactly one shape of browser-to-browser P2P that satisfies the law completely, and it is worth naming precisely because it marks where "impossible" stops.

law-compliant — user brings the bytes

If the user already has the file locally (File System Access API or drag-and-drop), the browser can seed it to other browsers over WebRTC with zero node in the byte path. Genuinely compliant. Genuinely peer-to-peer.

The catch is the whole point: it requires already possessing the content. It does not play an arbitrary magnet the user lacks — which is the question this lane was asked. That is the sharp boundary between possible (user brings bytes) and impossible (arbitrary magnet, no local copy). Everything on the possible side of that line is shipped and proven elsewhere in this report set; everything on the other side is what this page rules out.

It is just not addressable from a web page.

what would change the verdict

Watch-list — honestly, not today

"Impossible" here is a statement about the transports and the swarm as they exist in 2026-08. Three things could move that line. None of them has moved it yet, and the last gate is not even technical.

DevelopmentWhy it would matterStatus today

WebTorrent enabled in CI, PR #24564		 The first time mainstream desktop seeders would speak WebRTC — real swarm peers a browser could actually complete a handshake with. ~late 2026, not shipped
libtorrent 2.1.x adoption 2.1.0 shipped 2026-07-09 with TORRENT_USE_RTC. Adoption by mainstream clients would populate swarms with WebRTC-capable seeders. shipped, not default
The social gate
wss endpoints in standard tracker lists		 Even with hybrid peers everywhere, browsers and peers never meet without a shared wss rendezvous in the magnet's tracker list. This is a coordination problem, not a code one. 0 of 25 trackers
Direct Sockets for the open web The single biggest lever: a browser could open raw TCP to a swarm peer directly — still the user's own machine, still no node we run. IWA/ChromeOS-only, not planned

Note the ordering. Even if every client shipped WebRTC tomorrow, the social gate is still shut: the measured reach of WebRTC-capable seeders for this content is approximately zero, and no amount of client capability fixes a tracker list that carries no wss endpoint. That is why the honest framing is not today rather than soon.

how much to trust this page

Verification posture

This verdict rests on two independent legs, and they fail differently — which is the reason to state both.

leg 1 — first principles

The four-transports argument and the bootstrap paradox are structural. They do not depend on any measurement, any swarm, or any moment in time. They would hold for a torrent with a million seeders.

leg 2 — live measurement

The proof harness observed the real swarm: 54 seeders, 76 TCP peers handed out, 0 browser-reachable WebRTC seeders against a random control of 0. Captured in test/novel-path/PROOF-OUTPUT.txt.

honest caveat — the swarm numbers are time-variable

Swarm health moves. The evidence-file provenance for this same target records it plainly: a later re-capture attempt on the exact YTS swarm found 0 reachable classic peers. So treat 54/301, 3/204 and 76 as the values observed at capture time, not as standing properties of the torrent. Nothing about the verdict depends on them holding — a swarm with more seeders or fewer changes the numbers, not the wall. The zero that matters (browser-reachable WebRTC seeders) is the one the mechanism predicts structurally.

One more thing worth stating plainly: no node we run carried a single file byte during this test. The measurement harness announces and probes; it does not download. The mission published nothing and pushed nothing — nothing left the machine.
