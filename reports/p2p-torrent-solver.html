1 · The #1 blocker, diagnosed with evidence

The claim was "the vendored WebTorrent bundle's client.add() stalls; ready never fires." A raw event-timeline harness (tools/proof/bt-diag.mjs + bt-diag.html: every client/torrent event stamped, env probed) shows the bundle is healthy — the stall is the magnet-metadata path, not the bundle:

[0.0s] ENV {"secure":true,"subtle":true,"opfs":true,"rtc":true,"sw":true}
[0.0s] BUNDLE ok ctor=function VERSION=3.0.21 WEBRTC=true
[0.9s] EVENT torrent-fetched 20792 bytes          <- sintel.torrent over plain fetch()
[0.9s] EVENT torrent.infoHash 08ada5a7a6183aae1e09d831df6748d566095a10
[0.9s] EVENT torrent.metadata
[0.9s] EVENT torrent.wire webSeed                 <- HTTP web-seed connected
[1.1s] EVENT torrent.ready                        <- "never fires"? fires in 1.1s from BYTES
[1.1s] EVENT torrent.warning Error connecting to wss://tracker.btorrent.xyz
[tick 40s] ready=true peers=1 dl=45547383 progress=35.2%   <- ~1.2 MB/s off the web-seed
  • Root cause: client.add(<magnet>) needs METADATA, which a browser can only get from WebRTC peers found via wss trackers. Every wss tracker fails from this network (ERR_NAME_NOT_RESOLVED / ERR_CONNECTION_REFUSED) → ready never fires. Adding the raw .torrent BYTES makes metadata instant and the web-seed feeds pieces with no tracker, no peer, no server.
  • Second, masked break: WebTorrent 3.x removed getBlobURL, and file.streamTo() only works after client.createServer({controller}) over a registered service worker — the old code never set that up, so even a ready torrent could not reach the <video>.
  • Third: js/torrent.js swallowed all client errors (old line 55), hiding every failure as a silent timeout.
