1. What it does

With the beta pill on, every visiting browser publishes a small event stream on the floor room iris-beta-v1 — join, view, play_req, play_resolved, playing, heal, seek, fail, error, leave, plus a 30-second hb heartbeat. Every event is sealed to the collector's pinned ECDH public key on top of the floor's own room seal, because the floor derives its room key from the room name and that name ships inside public JavaScript. One layer would mean any reader of the site's source could see what strangers are watching; on an adult site that is not a "for now" we can accept.

The uplink is the other half of fire17's ask — testing a fix on a real live client in a real scenario instead of guessing. The collector can send a command back to one specific browser, and the browser will run it only after four independent gates pass.

3. The four C2 gates

A command frame is {t:'cmd', to, nonce, cmd, args, ts, sig}, sealed to the client's ephemeral public key and signed by the collector's control key. It must clear all four:

#GateWhy
1Decrypts with this tab's ephemeral private key, and to is this client's cid or '*'The key is minted at join, published as cpk, never stored, and dies with the tab. Per COMMON's RULING 2026-08-23, addressing is a plain cid string compare while sealing uses the full cpk — the two are deliberately decoupled, and no JWK-object equality exists anywhere in the client. Another client's telemetry on the same room simply returns null and is ignored.
2ECDSA-P256 signature verifies against the pinned CTRL_PUB_JWK Sealing proves nothing about who sent it — the room is joinable by anyone. Only frames signed by ~/.iris-beta/ctrl_priv.jwk can act. The signed bytes are the ruling's exact sign-input (below), and the client REBUILDS that object in the fixed key order rather than trusting the received JSON's ordering, so sign and verify cannot disagree.
3nonce unseen (ring of 400) and ts within ±120 s A captured frame cannot be replayed later, and a stale broker redelivery cannot re-fire a command.
4cmd is a key of the fixed HANDLERS map No eval, no Function(), no dynamic dispatch — the string can only ever index a hardcoded map. Anything else is dropped and reported as cmd_drop.

The canonical allowlist, held as a single byte-identical const (C2_ALLOWLIST, js/hp-beacon.js:285) that the handler map is checked against at load so the two can never silently drift: ping snapshot collectlog reload play pause resume seek goview setbeacon toast heal. heal forces the client's healStream('c2-test') — driving the reconnect path on a real live client is a primary reason C2 exists. Every executed command answers with ack {nonce, cmd, ok, detail}. The uplink obeys the pill exactly like the downlink: with telemetry off, every inbound frame is ignored. And whenever a command runs, a chip reading "🛰 remote test in progress" appears on that browser — never silent control.

One interop detail worth keeping. beta/cmd.mjs sends {...body, sig} with no t:'cmd' field. This client accepts a frame whose t is absent and rejects only a wrong t. Had that check been strict, every command from the real sender would have been refused silently, with no ack. Do not tighten it.

DEFECT-3, found by the collector lane and fixed here. join is emitted once; if it flushes before a relay is up the frame is gone (QoS0 keeps no history) and the client sits in the roster with no cpk, permanently uncommandable — their only remedy was asking the human to reload. Every heartbeat now carries cpk, so such a client heals itself within 30 s. The collector must therefore learn cpk from any event carrying it, not only from join.

5. Honest verification status

Verified live: the downlink end to end (browser → public broker → collector private key), the uplink end to end (signed command → executed → state + ack back), forged-signature rejection over the real broker, off-means-off (zero emits, zero frames, zero WebSockets), the consent chip, the heartbeat inside 35 s, and the absence of any IP-shaped string in a join.

NOT yet live-verified — stated plainly:

  • The playback emits. play_resolved, playing/ttff, heal, seek and fail need a real torrent and a live engine to fire. Their code paths are one-liner, window.HPBeacon &&-guarded, and syntax-checked, but no event of those kinds has actually crossed the wire yet.
  • The heartbeat's playing branch. Only the idle branch was observed (playing:false, engine:'idle'). The populated ih/t/buf/healN fields come from the same probe but have not been seen with a real session open.
  • The deployed site. Everything was proven against a local static server. Nothing has been pushed — deploys are the orchestrator's call, and nothing leaves this machine without fire17's confirmation.
  • The collector's command sender. CLOSED — see the cross-implementation section above. Both sides agree byte-for-byte on the ruling's sign-input and the real sender drives this client end to end.
  • The heal command against a real engine stream. Proven only in its honest negative: with no engine session open it acks ok:false. Forcing an actual healStream() reconnect on a live client is the single most valuable remaining test.
  • The rate cap and the error collapser were not driven to their limits (20 events / 10 s; identical errors inside 60 s). Logic is straightforward but empirically unexercised.
  • Day-one service-worker staleness. The build bumps the SW version, so a cached old app should pick the beacon up after one reload. Untested here.

6. Handoffs

Wire contract, as implemented (COMMON RULING 2026-08-23). Frame: {t:'cmd', v, to, nonce, cmd, data, ts, sig}, JSON, sealed with sealTo(clientCpk, …). The signed bytes are exactly: 
UTF-8( JSON.stringify({ v, to, nonce, cmd, data, ts }) )   // that key order, no `sig` present

ECDSA P-256 / SHA-256, raw r||s, base64url in sig. data defaults to {} on both sides. to is the target's cid or '*'. Freshness ±120 s, nonce ring 400 per tab. An earlier 'hpcmd|…' string form this lane had improvised was REPLACED by the ruling and no longer exists in the client — the ruling's form is the only one accepted, and it is proven live.

  • Keys are pinned and real, taken from node beta/keygen.mjs --print-pub and --print-ctrl-pub: PUB_JWK at js/hp-beacon.js:58, CTRL_PUB_JWK at :65. Rotating either key requires redeploying this file — if it is ever reset to a PASTE_ placeholder the beacon queues instead of sending, and refuses every command, rather than feeding the collector decrypt failures.
  • The collector should expect cpk on join and keep it in the roster; it is per tab, so a reload produces a new one.
  • New event kinds this lane added beyond COMMON's list, all store-only: ack, pong, state, log, cmd_drop. cmd_drop is worth surfacing in the realtime feed — it means someone sent this client a command it refused.

7. Divergence from the brief

One, logged in the journal and the oracle's terms: the brief assigns the join/leave emits to js/app.js. They live in js/hp-beacon.js's own boot and pagehide handlers instead. If app.js's boot() ever throws — precisely the moment telemetry matters most — an app-hosted join would never fire, and the client would be invisible exactly when it is broken. Everything else (view, engine, play_req, the pill) is in app.js as specified. Nothing else in the oracle diverged from reality.
