The complaint

User feel-test, verbatim: “changing the ammount of rows doesnt work also in the board tab — its not allowing me to zoom or navigate.”

Task 1 — root cause

The board is a WallView built as { layout:"wall", rows:3 } with the default cells — 160×240 (a 2:3 poster), gap 46, so the vertical pitch is 286 px. layoutWall then capped the row count to what fits the viewport without clipping a cell:

var maxRows = Math.max(1, Math.floor((viewport.vh + gapY) / PITCH_Y));
var rows = clamp(config.rows | 0, 1, config.maxRows);
if (rows > maxRows) rows = maxRows;                 // ← the clamp

With a 286 px pitch, maxRows evaluates to only 2–3 at a normal window height — often 2. So the higher row counts were silently discarded. Worse, the reversion was written back into the engine's state: relayout does if (res.rows) rows = res.rows, and layoutWall returned the clamped value — so setRows(5) became rows = 1–3 permanently, and every resize and every 2.5 s content poll re-clamped it too. The row dots, the number keys, and setRows() all appeared dead, and 100 items forced into one or two very long rows is exactly what “can't navigate” feels like. (The pan/zoom machinery itself was never broken — it was the single mega-row that made the board feel stuck.)

Task 1 — the design call

Three options were on the table: (a) honour the requested rows and let a tall multi-row wall be panned; (b) shrink the cells so N rows always fit; (c) a hybrid. I chose (a).

  • It keeps the wall's feel. A Cooliris-style wall is meant to be flown around — cursor-anchored zoom to survey, drag to roam. computeBounds() already unlocks vertical pan the moment content is taller than the viewport, and the wall is vertically centred on its origin, so more rows simply grow the wall symmetrically around the gaze. Nothing new was needed to make it navigable.
  • No poster is ever clipped mid-cell — whole rows sit off-screen until panned to, which is the point of a wall, not a bug.
  • (b)/(c) change the feel (tiles shrink to postage stamps at 5 rows) and add code for no benefit. Per the wall's own doctrine the row-per-catalog “Netflix” shape already exists as the separate catalogRows layout.
  • A row change stays a non-arrival relayout (relayout(false)), so the camera holds and the tiles reflow around the fixed gaze — consistent with hp-motion's arrival-vs-non-arrival rule and task 2's no-yank requirement.

The fix is the removal of the clamp: rows = clamp(config.rows|0, 1, config.maxRows) and nothing more. Because the returned res.rows now always equals the request, the write-back is idempotent — a resize or poll can no longer revert the user's choice.

Task 3 (escalation) — live-thumbnail previews

Turning on live previews for hundreds of feeds can't use hundreds of <video> elements (browsers cap at a few dozen; each HLS decode is heavy). The cheap primitive is a small <img> per tile, re-pulled periodically — no video decode, scales to hundreds. This lane owns that cheap-many half; the focused tile's real motion <video> overlay is hp-stream's.

Rather than build a parallel loader, the driver rides the wall's existing image pipeline — the same cache, the same concurrency-capped queue/pump (MAX_LOADS, the “laundromat”), and the same off-thread decode()-then-swap. A dedicated tl.live slot wins in the draw's src (so the reflection follows it too); a cache-busted, single-use URL is dropped the moment it decodes so the cache never grows.

Honest verification notes

  • Live-preview real-source fetch is unverified from this lane. The refresh/stagger/cap/decode/toggle/reduced-motion mechanics were all confirmed live with a local test source; the actual https://thumb.live.mmcdn.com/riw/<room>.jpg pull (CORS, cadence, content) was not exercised — the board's catalog carries no live items, and I would not drive the automated browser at a real cam CDN.
  • Field contract handed to hp-stream (via coordinator). The default resolver reads item.liveThumb (a full URL) first, else derives the Chaturbate URL from item.liveRoom or an id of the form chaturbate:<room>. Any of the three works out of the box; otherwise wall.setLiveThumbURL(fn). Turning previews on is wall.setLivePreview(true) — app.js is frozen in this lane, so whoever owns the previews UI wires that call.
  • Aspect on a dual item. A live pull refits the cell to the snapshot's aspect; on toggle-off clearLive() restores the base image's aspect. A cam catalog that wants a wide cell is a data/layout decision (hp-stream/catalog), out of this lane's scope.
  • Automation caveat. agent-browser mouse wheel did not dispatch to the canvas in this harness, so wheel zoom was verified by dispatching a genuine WheelEvent through a test hook — it exercises the real onWheel/zoomAt path. Pointer events (drag-pan) dispatched normally.
  • No fabricated counts. Every row count in this report was screenshotted and cross-checked against getState().rows; the served js/wallview.js was byte-verified equal to the worktree copy before trusting any behaviour.
