Direct-P2P Browser Torrent

A browser pulled a whole 68,086,404-byte clip from another browser while the only server in the picture was already dead. The signaling node carried zero file bytes, got SIGKILLed the instant the DataChannel opened, and the transfer still finished at 100% with the video playing. This page is the honest account of what that proves — and, just as carefully, what it does not.

the constraint everything is judged against

The law

Any node we run may relay handshakes/signaling ONLY. It must NEVER carry file bytes.
Files flow peer→browser directly, or not through us. A bridge/proxy that re-serves
torrent bytes to the browser VIOLATES the law and is a FAILED result — even if it "works".

Every claim below is scored against that sentence and nothing else. "It played" is not a pass. A design only passes if the bytes never touched a machine we operate. That standard is what makes one half of this lane a genuine result and the other half — the torrentio bridge — a failure we are obliged to report as a failure, no matter how well it appeared to work.

lane 1 · deliverables

What was built

1. The compliant WebRTC peer↔peer path

The topology is three nodes. A is a browser that wants the clip. C is a browser that already holds it. B is server/relay/signal.mjs — roughly forty lines over the ws package whose entire job is to forward SDP offer/answer and ICE candidates between the two peers of a room. It never sees a media byte; its own header comment states the point plainly: once A and C reach connected, "THIS PROCESS IS NO LONGER ON THE PATH."

The proof harness test/relay-punch/prove-rtc-killb.mjs makes that claim falsifiable rather than rhetorical. It brings B up, lets A and C handshake through it, and then SIGKILLs B the instant the RTCDataChannel opens — while bytesRecv is still 0 — and verifies the process is genuinely gone before any payload moves. The entire clip then streams A←C over the direct wire, to completion, with B dead and both peers observing their signaling sockets closed.

2. The self-sustaining swarm

prove-selfsustain.mjs pushes it further and removes the origin. C seeds; browser A takes a full copy; a second fresh leech A2 joins; then the tracker B is SIGKILLed and C is closed at the same moment, at 8.7% progress. A2 finishes to 100% from browser A alone. Once one browser holds the bytes, the content survives with no tracker and no original seeder — the swarm is genuinely browser-to-browser.

3. Self-seed playback with no backend at all

tools/proof/self-seed-proof.mjs builds a .torrent for the catalog's Big Buck Bunny mp4 with a url-list pointing at a static URL on the same host that serves the app — plain files and HTTP Range, i.e. what nginx, GitHub Pages or S3 already do — and a magnet carrying ws= and xs= with zero trackers. It plays through the real Player, headless. No engine, no resolver, no backend.

4. The transport ceiling, and the metadata stall it caused

The header of js/torrent.js states the hard ceiling verbatim: a browser can only reach WebRTC "web peers" (via wss:// trackers) and HTTP web-seeds (BEP19, magnet ws= or the .torrent's url-list). It cannot open TCP/uTP peers and cannot use the DHT. Torrentio magnets — infoHash plus udp/dht only, no wss, no web-seed — therefore have zero browser-reachable sources and can never play in-browser; they still need the node engine on :11470.

That ceiling produced a real bug with a real fix. client.add(<magnet>) waits for metadata, which a browser can only obtain from WebRTC peers found through wss trackers; when those trackers are unreachable, ready never fires — the stall. The bundle (WebTorrent 3.0.21, vendored) was healthy all along: adding the raw .torrent bytes fired infoHash, metadata and ready in about a second. The fix is to notice that our own catalog magnets always carry xs=<.torrent url>, fetch that .torrent in-browser, and add the bytes. Metadata becomes instant and the web-seed supplies pieces with no tracker and no peer needed. Playback needed a second piece: WebTorrent 3.x removed getBlobURL, so file.streamTo() runs through the service-worker bridge — ensureServer() registers the vendored /sw.min.js at root scope.

5. The honest fallback for what we cannot play

For TCP-only magnets the browser genuinely cannot reach, the app does not pretend and does not proxy. Every torrent stream row carries a 📋 magnet copy control (js/app.js ~1937–1966; a <span> rather than a nested button, stopping propagation so copying never triggers playback). copyMagnet() uses navigator.clipboard.writeText with a legacy fallback and a toast. The user gets the magnet for their own client. Bytes are never routed through us — which is exactly what the law demands when the answer is "we can't."

the part that failed — reported as a failure

Where the law bites

law violation — the torrentio bridge

server/relay/hybrid-seed.mjs (node "C") joins the classic swarm over TCP/uTP/DHT, downloads bytes it did not previously hold, and re-serves those exact live pieces to the browser over WebRTC. On the real YTS Spider-Man magnet it held 0 bytes up front, leeched 99,532,800 B live from 2 classic peers, and forwarded them to the browser. Its own source comment says it "re-seeds those exact pieces to browser A."

That is a contentless node we run forwarding live pieces — a byte-path relay — and the law forbids it in one sentence. The earlier prove-torrentio-video.mjs run "worked": transport persisted past killing signaling node B. But it worked by routing file bytes through a machine we operate. It is a FAILED result that was mislabeled as a pass, and we are correcting the label here rather than quietly keeping the win.

The measured record of that run, from torrentio-video-real-timeline.json, is worth stating precisely, because it also shows the second thing that went wrong:

So the kill-B evidence proves exactly one thing — that signaling node B is off the path. It does nothing to make node C compliant. And even setting the law aside, the clip never played. Two independent reasons the bridge is not a browser-first win.

the sharp boundary

The compliant shape requires both sides to speak WebRTC. Where that holds — a browser peer that genuinely holds the content, or a web-seed the browser can reach over HTTP — the law is satisfied with room to spare, as the green evidence above shows. Where it does not hold, an arbitrary TCP-only magnet the user does not already have cannot be delivered to a browser at all without breaking the law. That is not a limitation of our effort; it is a property of the four transports a browser can open. The full proof of that impossibility, with the measured swarm data behind it, is in physics-verdict.html.

Verdict

lane 1 — law-compliant direct-P2P browser torrent

Proven, at byte level, with committed evidence: a browser received 68,086,404 bytes from another browser over a direct WebRTC DataChannel while the only node we ran was already a dead process, having carried 0 file bytes. The swarm then proved it can outlive both its tracker and its original seeder. The self-seed path shows the same content model working from nothing but a static file host.

What we will not claim: that this plays an arbitrary magnet. It does not, it cannot, and the honest product answer for those is the copy-magnet button, not a proxy. Three of the six supporting claims rest on committed harnesses whose run output was not captured, and they are marked unverified above rather than folded into the win. Nothing was published or pushed; nothing left the machine.
