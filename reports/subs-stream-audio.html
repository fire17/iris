Window-Scoped Subtitle Audio

Whisper auto-sync used to do nothing on a torrent or an HLS stream. It needed decodable audio, and the only way to get it was to decode the whole file — impossible for a full-length film. This lane cuts out just the twenty seconds the matcher actually listens to.

2026-08-21 commits 8a1974e · 717934d · c8681af merged 516b06c verified in headless Chrome, all media muted at load

The gap, and the insight that closed it

why it no-opped

Whisper needs PCM. The engine's only way to produce it was decode(), which built an AudioBuffer for an entire file. That is fine for a short clip and impossible for a two-hour film, which decodes to gigabytes of PCM — and a live HLS stream has no whole file to decode at all. Tapping the playing <video> was not an alternative either: createMediaElementSource() re-routes the element's audio into WebAudio and would have muted the user. So auto-sync correctly did nothing, and subtitles stayed raw.

The insight is that the coherence matcher never wanted the film. It listens around the first-sentence and last-sentence subtitle timestamps — roughly two twenty-second windows. The problem was never decoding; it was seeking. Once you can cut an arbitrary window out of a byte source, the entire existing matcher works unchanged.

The engine now accepts a window provider — an object exposing audioWindow(startSec, durSec) that returns encoded bytes for just that slice. transcribeWindows() detects one automatically, decodes each window alone, and releases it. The matcher in js/subs-autosync.js required no change whatsoever.

Per-path verdict

proven, partial, or walled — each with what was observed

Torrent — bytes from the WebTorrent file

Proven

Byte ranges are pulled straight from the file window.BT is already streaming, via file.stream({start, end}). No new transport, no server, no CORS surface — the bytes were already arriving peer-to-peer. The MP4 sample tables are walked to map a time window onto sample byte ranges, which are coalesced into a couple of reads and re-framed as ADTS.

file Sintel.mp4 length=129,241,752 B window t=60s dur=20s -> 1,097,223 B read (0.85%) PCM 48000 Hz · 6 ch · 20.01 s · rms 0.04345 words "I'm not sure if" @ 70.32 s

That is real Sintel dialogue, recovered from a film we never downloaded.

HLS — segments via the hls.js fragment list

Proven

The time window is mapped to segment URLs by reading hls.js's own fragment list read-only — we never call loadSource, attachMedia, startLoad, never change level, never seek. The segments are fetched separately and demuxed (TS: PAT → PMT → audio PID → PES → ADTS; fMP4 handled too). Playback is untouched and stays unmuted for the user.

window t=80s dur=20s -> 163,464 B fetched PCM 48000 Hz · 2 ch · 20.02 s · rms 0.02086 words "You" 81.60 -> 82.66 "are" 82.66 -> 85.02 "alone." 85.02 -> 87.00

Offline against a real captured segment the demuxer reports sniff='ts', 216 ADTS frames at 22050 Hz stereo, buffer beginning ff f1 — a valid AAC-LC syncword.

Direct URL — HTTP Range

ProvenCORS-gated

The same MP4 window extraction over plain range requests. This also lifts a pre-existing ceiling: the old whole-file decode refused anything over 80 MB, so long direct-URL films had silently lost auto-sync too. Identical numbers to the torrent lane, since it is the same file by a different byte path.

The honest limit is CORS. A <video> may play a cross-origin file opaquely, but fetch() cannot read its bytes without access-control-allow-origin. Verified directly against a real host:

$ curl -sI -H "Origin: …" -r 0-100 https://media.w3.org/…/trailer.mp4 HTTP/2 206 content-range: bytes 0-100/4372373 (no access-control-allow-origin header)

On such a host the provider yields nothing and auto-sync degrades to raw subtitles. There is no browser-only way around it — the same class of wall as the transport verdict. Torrent and HLS are unaffected: torrent bytes never touch fetch, and an HLS stream that hls.js can play is CORS-enabled by definition.

In-app convergence to a measured offset

Partial — mechanism proven, convergence not

Driving the real app against a real 129 MB streamed film, the plumbing demonstrably works end-to-end: the player builds the provider, whisper runs on stream audio, and nothing leaks.

audioSource url:Sintel.mp4 windowMisses 0 whisper 99 calls · 412 words · 15 windows bytes pulled 53,632,998 audio leak none phase available measured offset 0

But it did not converge to an offset within the run, and it pulled 53.6 MB doing it — far more than the 1.09 MB a single window costs. The cause is budget, not audio sourcing: the back-anchor windows are up to 160 s long and Sintel's track is 448 kbps 5.1, so each one is expensive. This is recorded as a FAIL in test/subs-audio/app-stream-sync-proof.mjs rather than dressed up. The fix is a budget change — treat large ranged sources as costly so they take the same reduced window budget the torrent and HLS providers already declare.

Non-AAC audio and MKV containers

Walled by scope

AAC-LC (mp4a.40.2) is what the extractors support. An AC-3, E-AC-3 or Opus track returns a typed error and auto-sync degrades to raw subtitles rather than emitting garbage that would produce a confident-looking wrong sync. MKV/WebM containers are not parsed at all — a torrent whose video is .mkv returns no provider. Both are deliberate: refusing beats guessing.

The finding worth keeping

whisper hallucinates into its own padding

Whisper always processes a fixed 30-second frame and pads a shorter clip with silence — and it dates words out in that padding. An early HLS run "passed" with the phrase "Thank you.", which is the single most notorious whisper hallucination on silence. Left alone it would have poisoned the matcher's anchor times with confident nonsense.

Rather than assume a threshold, this was measured (test/subs-audio/clip-times.mjs):

On real speech the clamp costs one word in forty-nine. On music it removes everything, which is the correct answer. The engine now drops any word starting past the clip's true duration and clamps the ends — nothing is invented, only impossible times are refused. A scan of ten windows of the public test stream found real dialogue in three; the other seven are music, and now honestly report zero words instead of a plausible lie.

Minor, noted not fixed: on the torrent and ranged-URL lanes the four returned word timestamps collapse to a single value (70.32 repeated for "I'm", "not", "sure", "if"). The words and the window are right, so first-instance anchor matching still works, but intra-phrase resolution is lost on that clip. It looks like degenerate cross-attention alignment in whisper-tiny on 5.1-downmixed audio, not a fault in the window path — the HLS lane on stereo returned properly spread times (81.60 / 82.66 / 85.02).

Guarantees held

the rules this lane was not allowed to break

  • Raw subtitles stay instant. Nothing in this path blocks display. A window that cannot be sourced resolves to zero words instead of rejecting, so a failure degrades to the raw cues rather than throwing at the user.
  • The user is never muted. No createMediaElementSource, no playback tap, no volume change. Every proof asserts it: across all runs, media elements observed muted=true volume=0, zero offenders, zero un-mute attempts.
  • No runtime CDN. The demuxers are hand-written and vendored in js/; no mp4box.js, no external fetch in app code.
  • Additive. The whole-file decode path still exists as a fallback; existing matcher tests still pass (test/subs-matcher.test.js → PASS: true).
  • Playback untouched. The HLS provider only reads hls.js's fragment list; the torrent provider only asks for byte ranges the client is already able to serve.

What is left

honest next steps, in order of value

  • Budget the ranged-URL provider as costly when the file is large, so it takes the reduced window budget instead of the full wide scan. This is the direct cause of the 53.6 MB in-app run.
  • Cap back-anchor window length for any costly source — a 160-second window is a poor trade when the anchor is a single sentence.
  • Land the in-app convergence proof once the budget is fixed: shifted real subtitles in, measured offset out.
  • MKV audio if torrent titles need it — most real-world torrent video is Matroska, and today those simply get no provider.

None of these are walls. The audio-sourcing question this lane owned is answered: a browser can obtain a decodable, arbitrary audio window from a streaming torrent and from an HLS stream, cheaply, without touching playback.
