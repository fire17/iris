1 · The verdict

The live site is genuinely fast. A cold visit paints the wall in 445 ms (median, n=3) over the real internet, well inside a budget that was written for localhost, and every one of the eight budget rows that can honestly be judged from a deployed static host passes. The 87 MB vendored whisper stack is confirmed lazy — exactly one 1,220-byte capability probe touches vendor/ on load. There is no performance defect to fix.

The service worker is therefore not a rescue. It is worth shipping for one specific, measured reason, and the naive case for it is wrong. GitHub Pages serves every asset with cache-control: max-age=600, so a repeat visit inside ten minutes is already near-instant from the browser's own HTTP cache — 88 ms first-contentful-paint, 56 of 58 resources served with zero network. A service worker adds almost nothing there, and reporting the cold-vs-warm delta as "what the service worker buys" would have been a serious overclaim.

The real finding. We waited out the full ten-minute freshness window and measured a genuine stale-cache return visit. Chrome did not revalidate cheaply — it re-downloaded all 17 own-origin assets in full, 194,111 bytes, with zero 304 responses. Wall-clock load went from 423 ms (fresh cache) to 525 ms, i.e. essentially a second cold load. So today, every visit more than ten minutes after the last one costs the user a complete 194 KB re-download of the app shell. That is the cost the shell cache removes, and it is the only honest headline for this change.

The 87 MB vendor stack — confirmed lazy

A regex for whisper|transformers|onnx|\.bin|\.safetensors|tokenizer across every request in three 45-second waterfalls plus six cold/warm loads matched exactly three URLs per run: js/whisper-engine.js, js/whisper-tiny.js, and one vendor/whisper-tiny.en_timestamped/config.json — a 1,220-byte capability probe from js/whisper-tiny.js:29. Zero model blobs: no .onnx, no .wasm, no tokenizer, nothing under vendor/transformers/. The lazy law holds. The only tightening available is deferring that 1.2 KB probe to first subtitle intent.

4 · The service worker (built + locally verified — NOT yet live)

What existed before. sw.min.js was a byte-identical copy of vendor/webtorrent-sw.min.js — the vendored WebTorrent 3.x streaming bridge, 1,297 bytes. It caches nothing, and it is registered lazily, only by js/torrent.js:93 inside ensureServer(), which runs only when a torrent stream is about to play. On a normal load the live site has no service worker at all — confirmed on the live site: navigator.serviceWorker.controller === null at every 400 ms sample across 45 s in all three runs, getRegistrations() returned [], and sw.min.js was never requested.

The design, and why each line is there

The new worker is 86 lines and ends with importScripts('vendor/webtorrent-sw.min.js'), so the vendored bridge stays pristine and unmodified. Ours registers its fetch listener first and returns without responding for anything it does not own, letting the vendored listener see the event untouched.

if (req.method !== 'GET') return;                        // HEAD pings from netmon.js
if (url.origin !== self.location.origin) return;         // Cinemeta, posters, CDNs
if (url.pathname.indexOf('/webtorrent/') !== -1) return; // the vendored bridge owns these
if (req.headers.has('range')) return;                    // never intercept ranged media
if (req.cache === 'no-store' || req.cache === 'reload') return;   // ← THE ESCAPE HATCH
if (url.pathname.indexOf('/vendor/') === 0) return;      // the 87 MB stack, never cached
The escape hatch is the whole safety argument. js/registry.js polls verified_sources.md and js/dev.js polls the core files — both with fetch(…, {cache:'no-store'}). Honouring that one flag preserves the live registry watch (budget row 4) and devmode hot-reload simultaneously, with a single condition. We did not assume the flag survives into the worker; we measured it in real Chrome: a worker probe reported request.cache as "default", "no-store" and "reload" for the three corresponding call sites. The verified_sources.md network-first rule below it is belt-and-braces for a future refactor that drops the flag.

The app shell uses stale-while-revalidate — instant paint from a versioned cache (hp-shell-v1), fresh copy fetched in the background — so a redeploy self-heals within one further load with no manual version bump. Install uses per-entry cache.add().catch() rather than atomic addAll(), so one 404 in a half-synced deploy degrades to a partial shell instead of leaving the site with no worker at all.

The honest reading of the local speed delta

Local warm DCL improved only 84.8 ms → 78.3 ms. That number is not the value of this change and must not be quoted as such. On 127.0.0.1 a revalidation round trip costs almost nothing, so eliminating nineteen of them saves almost nothing. The saving scales with round-trip time, and the live measurement in §1 is what makes the case: on the real deploy a stale return visit re-downloads 194,111 bytes across 17 requests with zero 304s. The shell cache turns that into zero network and a cache-served paint. We have not measured that improvement live, because the worker is not deployed — it is a projection from two measured endpoints, and it is labelled as one.

6 · Is it safe to rebuild and push?

Yes, with one caveat about timing. A full sha256 audit of the deployed tree found 13/13 files byte-identical between .deploy/ and what the live site serves. Comparing the source tree against .deploy/, exactly two files would change the live site:

  • sw.min.js — the intended change.
  • index.html — the registration line, which is what actually switches the worker on for every visitor.

Three other dirty files (verified_sources.md, both vendor/transformers bundles) are uncommitted in the source repo but were already built into .deploy and are already live, so a rebuild is a no-op for them. Nothing from server/, test/, node_modules/, tools/, the root docs or the agent worktrees can ride along — build-deploy.sh copies an explicit whitelist. The >95 MB per-file gate passes; the largest single file is the 29.3 MB whisper decoder.

The caveat is timing, not scope. build-deploy.sh snapshots the working tree at the moment it runs, and several agents are editing this repo concurrently. Building at the wrong instant can ship a half-written file. Verify sw.min.js is 245bdbd2… immediately before building.

INCIDENT — MY LANE, DISCLOSED

Proving budget row 4 requires editing verified_sources.md while the app is running. My proof agent did that against the real repo and restored two of three probe rows, leaving one behind. A concurrent agent ran build-deploy.sh and pushed inside that window, so the row | PERF PROBE SW 2 | demo | …Sintel_720_10s_5MB.mp4 | … | reached the live site and rendered as a bogus demo card on the honest ledger. Content was SFW, so no scope law was breached, but a fabricated registry row is exactly what this product must never have.

Resolved in source. The row is removed and verified_sources.md is byte-identical to its pre-probe state, sha256 6bd1979b…. A second copy of the row propagated back once via a probe script's own stale backup; that was cleaned too and a guard was armed for the rest of the session. The live site stays wrong until the next rebuild + push, which clears it automatically. All subsequent live-watch testing was moved to an isolated /tmp copy, which is where the 4/4 row-4 proof above was taken.

Lesson for every lane: this repo is built and pushed on a short cycle, so any mutation of a build-copied path can go public within minutes. Treat index.html, style.css, js/, assets/, vendor/, verified_sources.md and .grand/reports/ as live surfaces, never as scratch space.

7 · Recommendations we did NOT apply

This lane owns only sw.min.js and one line of index.html. The following are measured observations for whoever owns the boot path — nothing below was changed.

  1. Eleven of the sixteen head scripts paint no wall pixel. player.js, torrent.js, netmon.js, dev.js, whisper-engine.js, whisper-tiny.js and the five subs-*.js total 98,211 of the 187,216 pre-paint wire bytes (52.5%) and are all loaded defer in <head>. Moving them behind the window load event is an estimated 85–110 ms off first wall paint. Risk to weigh: player.js must still be resident before a click, or budget rows 1 and 2 suffer — this trade needs measuring, not assuming.
  2. Idle polling never lets the page go quiet. registry.js polls every 2.5 s and netmon.js HEAD-pings every 1.5 s, costing ~29 KB per 45 s, forever, and the page never reaches network-idle. Correct for a live registry; worth a backoff when the tab is hidden.
  3. The 1.2 KB whisper probe on every load could be deferred to first subtitle intent.
  4. The 30 net::ERR_ABORTED per run are not real failures — they are netmon.js HEAD pings cancelled by navigation. Harmless, but they will show as errors in any synthetic monitor watching this site.

8 · Verification status (honest)

  • All live numbers come from one macOS machine, one network, through the Fastly edge cache-fra, headless Chrome 151.0.7922.174 at 1440×900. One vantage point, not the user experience.
  • Every live response carried x-cache: HIT with an age of 5–150 s — even our cold runs hit a warm CDN edge. A visitor whose nearest edge is cold will be slower than any number here.
  • Sample sizes are n=3 (n=4 for the registry-watch row, n=10 for curl root latency). Median with min/max. There is no p95 in this data and none should be quoted.
  • Variance is large on some metrics: cold FCP ranged 312–680 ms, cold first-poster-tile 676–4211 ms. Single figures for those are not meaningful.
  • Budget row 3's threshold was authored for python3 -m http.server; we judged it against a CDN. The comparison is indicative, not a pass against the written budget.
  • transferSize reads 0 both for cache hits and for cross-origin responses lacking Timing-Allow-Origin, so it is not a cache-hit counter. Warm "193 KB" is decompressed-from-cache payload, not bytes off the wire; real warm first-party network cost was ≈ 0.
  • Cold and warm did not render the same workload (7 wall items cold vs 80–200 warm), so the cold→warm delta mixes a cache effect with a different amount of work.
  • The service worker was verified functionally and locally, never live. The stale-visit saving is a projection from two measured endpoints, not an observed live improvement.
  • Not measured: offline behaviour end-to-end, throttled/mobile/low-end devices, a non-headless run, a second network vantage point, budget row 11 (60 fps / zoom skew), and row 8's repo-side audit.
  • Measurements were taken while other agents edited the source tree. The deployed site did not change during the live measurement window, so the live numbers are unaffected; source-file statements are pinned to the sha256 values recorded above.
