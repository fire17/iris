What was built

The player now carries a complete, self-contained subtitle stack — the "known highest standard, fully featured" baseline described verbatim in the source. It fetches, merges, decodes, renders, and persists subtitles without any server of ours in the loop. The user picks a language and gets subtitles; everything else is automatic.

How it works

poster / stream→ gather sources→ merge + dedupe→ group by language→ decode → WebVTT→ paint overlay

Sources — merged, deduped, grouped by language

Three source classes are combined by subSourceList(type, id, extra) and returned as a single deduped list keyed by URL:

  • Subtitles already carried on the stream or item metadata.
  • Every installed Stremio addon that declares the subtitles resource for this type/id (discovered via Addons.supports).
  • The public OpenSubtitles v3 addon — https://opensubtitles-v3.strem.io, CORS-open and, per the source, verified live. It is always appended as a default so a language list exists even when no other addon is installed.

Each source is queried as <base>/subtitles/<type>/<id>[/extra].json with an 8-second timeout and cache: force-cache. Series compose their id as imdb:season:ep, so the picker tracks the exact episode. Results are grouped by language with English first, then alphabetical, and a count badge appears when a language has more than one candidate.

Rendering — native parse, own overlay

The browser's native WebVTT parser fills a hidden <track>; the player copies its cues once and paints the active ones into its own overlay element (S.el.subCue). That indirection buys full, cross-browser-identical control over text size, colour, background, vertical position, and a live manual sync offset — and lets an auto-sync lane feed synced cues in without a competing second renderer. The player sets window.__subsRendererPresent = true so any auto-sync module knows on-screen rendering is already owned and never self-attaches a duplicate track.

Formats — SRT / SSA(ASS) / VTT, charset-sniffed

subsToVtt() decodes raw bytes before converting. The charset path is explicit: a UTF-8, UTF-16LE, or UTF-16BE byte-order mark is honoured first; otherwise a strict (fatal) UTF-8 decode is attempted; failing that it falls back to windows-1251 when the bytes look Cyrillic, else windows-1252. WEBVTT passes through (with comma→dot timestamp normalisation); [Script Info]/Dialogue: is parsed as SSA/ASS by ass2vtt(); everything else is treated as SRT by srt2vttFull(). Timestamps are normalised by subPadTs() and styling tags are stripped.

The last-used off/language is auto-applied the next time the player opens, and styling persists too. The config is merge-safe and shared with the auto-sync lane through a single key, so both lanes can co-exist without stomping each other.

The law-compliance story

no node in the byte path

Every subtitle byte is fetched by the browser directly from a third-party content endpoint — the same class as an <img src>. The default OpenSubtitles v3 source is CORS-open, so no proxy of ours is needed and none exists. This lane never touches the law — no node we run relays or re-serves subtitle content; the browser talks to the addon, or to nothing.

the honest gap

The standard, fully-featured live subtitle system shipped and is live in the player. The whisper auto-sync engine — the blazing-fast coherence-and-fine-sync half of the original goal — did not ship as code: js/player.js only capability-detects a window.SubsAutoSync module and hands it a clean interop surface (SubsSource.list, the shared hp.subs.cfg config, the __subsRendererPresent handshake). Every integration seam for it exists; the engine behind the seam does not. Reported here rather than implied as done.
